## 0. Werdykt w skrócie

- **Czy się buduje?** Tak. `make all` przechodzi ścieżką awaryjną `gcc -m32` (brak `i686-elf-gcc`) z `-Wall -Wextra -Werror` bez żadnego ostrzeżenia kompilatora. `ld` zgłasza tylko ostrzeżenia RWX / executable stack.
- **Czy bootuje?** Tak, **ale tylko w QEMU i tylko z podpiętym dyskiem ATA oraz co najmniej 32 MB RAM**. Dochodzi do pulpitu 1920×1080 z topbarem, dockiem i kursorem. Bez `-hda` jądro wisi w sterowniku ATA, a to jest dokładnie konfiguracja z `make debug`. Przy 20 MB RAM start zatrzymuje się zaraz po włączeniu pagingu.
- **UTERM.ELF, ABOUT.ELF, UTEXTEDIT.ELF:** wszystkie trzy startują jako procesy Ring 3 z osobnym CR3 i dają się zamknąć (Esc, Q, przycisk X). UTEXTEDIT **nie umie zapisać ani otworzyć pliku** („Save arrives in next step”). Stary edytor w jądrze, który to umiał, jest wkompilowany, ale nigdzie się go nie da uruchomić.
- **Stan ogólny:** działające demo integracyjne na kruchym fundamencie. Najtrudniejsze elementy są zrobione i działają w runtime: tryb chroniony, IDT, TSS/`esp0`, CR3 per proces, `iret` do Ring 3, walidacja wskaźników przez page-table walk, sprzątanie procesów po faultach, TTF z antyaliasingiem, WM. Są jednak błędy fundamentalne: brak jakiejkolwiek synchronizacji w wywłaszczalnym jądrze, GemFS piszący bez sygnatury po surowym dysku, niezerowany BSS, brak detekcji pamięci, sterownik ATA bez timeoutów. Do tego około 17% plików źródłowych to martwy kod, a `AGENTS.md` w wielu miejscach mija się z rzeczywistością.
- **Rekomendacja:** **remont, nie przepisywanie od zera.** Tyle że remont generalny: 4 moduły trzeba przepisać od nowa (boot chain, alokator sterty, ATA+GemFS, model współbieżności syscalli), a resztę wyczyścić. Kolejność i uzasadnienie są w [§8](#8-rekomendacja-remont-nie-rewrite--ale-z-przepisaniem-4-modułów).

### 2.3 Testy obciążeniowe (funkcjonalne)

- **10× UTERM bez zamykania:** otwiera się 8 okien (limit `CONSOLE_MAX_SESSIONS`), dziewiąty i dziesiąty proces kończą się czysto:
  ```
  [PROC] Spawned PID=12 UTERM.ELF
  [USER] UTERM2 failed to open console
  [PROC] Reaped PID=12 exit=1
  ```
  Obsługa błędu jest poprawna, ale użytkownik nie widzi żadnego komunikatu. Wszystkie okna otwierają się dokładnie w tym samym miejscu (brak kaskady).
- **25 cykli otwórz/zamknij UTERM:** `reaped: 25, alloc-fail: 0, panic: 0`. Wycieku ramek ani sterty przy tej skali nie widać.
- **Dowód na brak synchronizacji (ważne).** W tym samym teście jedna linia logu wygląda tak:
  ```
  [APP] Opening: User Terminal
  [PROC] Spawned PID=5 [DOCK] Window Registered
  [FOCUS] Dispatching event. Type: WINDOW
  [CONSOLE] Opened PID=5 handle=5
  UTERM.ELF
  ```
  Wątek jądra (task 0) był w połowie `serial_print` w `process_spawn_user_from_file`, gdy przerwanie zegarowe przełączyło na nowy proces. Ten proces **zdążył wykonać syscall `console_open`, czyli `kalloc` + `wm_add_window` + rejestrację w docku**, zanim task 0 dokończył swoją linię. Tym razem przerwany był log. Równie dobrze mógłby to być `kalloc`, iteracja po liście okien albo sekwencja komend ATA (§4, problem nr 1).

### 2.4 Start bez dysku twardego (tak robi `make debug`) — zawieszenie

```
[EVENT] Event Queue initialized
[ATA] Driver Initialized (PIO Mode)
                                   ← nic więcej
(qemu) info registers  →  EIP=0010dc90 ... CR0=00000011
```

`0x10dc90` to pętla `ata_wait_drq()` wewnątrz `ata_read_sector` (disasm: `in (%dx),%al; test $0x8,%al; je 10dc90`). Nie ma timeoutu ani sprawdzenia obecności dysku (`drivers/ata.c:19-27, 31-51`). Udokumentowany workflow debugowania (`make debug` + gdb) nigdy nie dojdzie więc do grafiki.

### 2.5 Mało pamięci

- **`-m 20M`:** log urywa się po `[PAGING] Enabled successfully`. Self-test pagingu bierze ramkę `0x019EC000` (~26 MB), której fizycznie nie ma, a sam QEMU kończy się wewnętrzną asercją (`qemu_mutex_lock_iothread_impl`). Źródło problemu leży w jądrze: sterta (24 MB) i pula ramek (do `0x02000000`) są na sztywno (`kernel/kernel.c:37`, `kernel/memory/paging.h:15-19`). Mapa E820 jest zbierana przez stage2 (`loader.asm:216-237`), ale nigdy nie trafia do jądra.
- **`-m 32M`:** działa, UTERM startuje. 32 MB to więc minimum „na styk”, bez żadnego sprawdzenia, a pula ramek pokrywa górną część RAM, gdzie firmware kładzie swoje tablice.

## 4. Top 10 najgorszych problemów (od najpoważniejszego)

1. **Wywłaszczalne jądro bez żadnej synchronizacji.**
   Task 0 (pętla GUI) jest wywłaszczany co 10 ms. Syscalle procesów (z IF=0, na stosie jądra procesu) wchodzą w ten sam globalny stan: `kalloc`/`kfree` (`console.c:484`), listę okien i focus (`wm_add_window`, `console.c:520`), tablice docka, `gemfs_write`/ATA (`syscall.c:265-292`) i klog. Task 0 może być w tym momencie w połowie `kalloc` (alokacje przy chybieniu cache glifów w trakcie renderu: `scanline.c:195`, `font.c:150`), iteracji po oknach (`wm.c:312-330`) albo wieloetapowej komendy ATA. Skutki są niedeterministyczne: korupcja sterty, listy okien albo przeplecione komendy dyskowe, czyli korupcja danych. **Potwierdzone w runtime** (§2.3: przepleciona linia logu z PID=5). Problem przekrojowy, dotyka każdego modułu.

2. **GemFS niszczy dane i nie jest systemem plików.**
   Bez superbloku i sygnatury pisze pod LBA 1–4 i od LBA 5 pierwszego dysku ATA, **przy każdym starcie** (seeding ELF-ów, `kernel.c:207` → `process.c:197-223` → `gemfs.c:70-76`). Na prawdziwym sprzęcie z podpiętym dyskiem niszczy nagłówek i tablicę partycji GPT (LBA 1–33) albo obszar bootloadera za MBR (np. `core.img` GRUB-a). Stałe sloty 8 KB, maksymalnie 64 wpisy, nazwy do 19 znaków, katalogi połowiczne, brak weryfikacji zapisu. Limit 8 KB przenosi się na **maksymalny rozmiar każdego programu userlandu** (`process.c:15`).

3. **Fundament boot/pamięć działa wyłącznie w QEMU.**
   - BSS niezerowany (`entry.S`, `linker.ld:41,45`), a część BSS wypełniana bajtami z obrazu.
   - Brak detekcji RAM: E820 zbierana i wyrzucana (`loader.asm:216-237`), sterta i pula ramek na sztywno do 32 MB (`kernel.c:37`, `paging.h:15`). Przy 20 MB start pada (§2.5).
   - Loader tylko z dyskietki CHS (`loader.asm:375-397`), stały limit 1120 sektorów przy 88% zajętości i bez kontroli w buildzie.
   - Wymagane **dokładnie** 1920×1080×32, inaczej `halt` (`loader.asm:288-328`).
   - BGA zakładane bez detekcji (`vbe.c:57-66`).

4. **Sterownik ATA bez timeoutów i obsługi błędów** (`ata.c:19-76`). Bez dysku boot wisi (§2.4), więc `make debug` jest bezużyteczny. Każdy błąd dysku oznacza wieczną pętlę. Zapis pliku przez syscall to do ~24 zapisów sektorów, każdy z flushem, przy IF=0: cały system stoi, ticki PIT się gubią.

5. **Granica Ring 3 jest szczelna w środku, ale dziurawa na brzegach.**
   - Wyjątki z CPL3 spoza listy {0,6,10–14} idą ścieżką paniki jądra i zatrzymują cały system (`isr.c:171-184, 231-252`). README twierdzi, że „faulted user processes are killed without panicking the whole kernel”.
   - Sprawdzenia zakresów w loaderze ELF mogą się przewinąć w 32-bitowej arytmetyce (`elf.c:88-91, 110`). Jednocześnie ELF-y w GemFS może nadpisać każdy proces (`SYS_file_write` bez uprawnień) i mają pierwszeństwo przed wbudowanymi (`process.c:109-116`). Loader musi więc traktować te dane jako niezaufane.
   - Segmenty userlandu RWX (`user_linker.ld:7`), `CR0.WP` wyłączony.

6. **Brak zarządzania stanem FPU przy wszechobecnym `float`.** Skala UI i rasteryzacja fontów używają x87 w 9 plikach jądra, **w tym w handlerze IRQ myszy** (`mouse.c:109-110`). Nie ma `fxsave`/`fsave` ani leniwego przełączania przez `CR0.TS`. Dziś chroni przed skutkami tylko to, że userland przypadkiem nie używa liczb zmiennoprzecinkowych.

7. **Model schedulera nie skaluje się poza demo.**
   - Bezczynny task 0 robi `hlt` na swoim kwancie, zamiast oddać procesor (`kernel.c:314`).
   - Brak blokowania (`TASK_BLOCKED` nieużywany), więc aplikacje kręcą się w `poll`+`yield`.
   - Stosy jądra 16 KB ze sterty bez stron ochronnych, stos użytkownika 8 KB (`paging.h:19`).
   - Stałe limity: 16 zadań, 8 konsol, 1556 ramek.
   - Wątki jądra (`task_create`) są zaimplementowane, ale nigdy nieużyte.

8. **Alokator sterty z epoki „Phase 3.1”** (`heap.c`): first-fit, scalanie tylko do przodu (fragmentacja rośnie z czasem pracy), zero ochrony przed double free i nadpisaniem nagłówka, alokacje w ścieżce renderowania (chybienia cache glifów). W połączeniu z punktem 1 to główny kandydat na trudne do odtworzenia awarie.

9. **Martwy kod, zdublowane podsystemy i regresje funkcjonalne po „migracjach” różnych modeli AI.**
   - 2 719 linii w całości martwych plików, −20%/−32% kodu i danych nieosiągalnych.
   - 4 silniki fontów, 2× `string.h`, 2× `glyph_t`, 2 systemy kodów klawiszy, 5+ kopii `strlen`.
   - Migracja edytora do userlandu zostawiła **edytor bez zapisu**, a działający stary jest martwy. Explorer kieruje pliki do edytora, który ignoruje ścieżkę.
   - Komentarze będące zapisem rozmów z AI, w tym niedokończone poprawki („WAIT… BAD.”, `primitives.c:146-147`).

10. **Dokumentacja wprowadza w błąd, a build nie ma podstawowej higieny.** Ponad 25 fałszywych lub nieaktualnych twierdzeń w `AGENTS.md` (§6). Makefile: bez zależności od nagłówków, reużywany obraz, kolizje nazw obiektów, brak kontroli rozmiaru jądra. Brak pliku `LICENSE` (README deklaruje MIT), a `font.ttf` to Inter na licencji SIL OFL 1.1, dołączony bez tekstu licencji.

Poza pierwszą dziesiątką, ale do naprawy: tekst nie jest obcinany do okna (`aa.c:62-66`); okna większe od ekranu i otwierane w jednym miejscu; proporcjonalny font w siatce komórek; pełny repaint 1080p w każdej klatce; `gfx_fill_circle` rysuje każdy piksel dwa razy; `window_t` wyciekają dla aplikacji bez `close`; spam `[TIMER]` z IRQ; RTC bez flagi UIP.

### 6.2 `README.md` vs kod (ogólnie trafny, ale)

- „faulted user processes are killed without panicking the whole kernel”: **tylko dla części wektorów** (§4, nr 5).

## 7. Co jest dobre (i warto to zachować)

- **Czysta kompilacja** z `-Wall -Wextra -Werror` na nowym gcc.
- **Rdzeń izolacji:** GDT z segmentami Ring 3, TSS z `esp0` per zadanie, CR3 per proces, mapowanie jądra tylko dla supervisora, ramka `iret` do Ring 3 zgodna z `registers_t`.
- **`copy_from_user` / `copy_to_user` / `copy_user_string`**: walidacja przez page-table walk z bitami U/W i limitami zakresu. Jak na hobbystyczny OS, zrobione dobrze.
- **Loader ELF:** sensowny zestaw walidacji (poza przepełnieniem arytmetycznym).
- **Cykl życia procesu:** spawn, exit, fault, zombie, reaping i zamknięcie okna zabijające proces działają (25/25 w teście). Limit konsol obsłużony poprawnie.
- **Renderowanie TTF** z gamma-poprawnym antyaliasingiem i cache glifów wygląda dobrze.
- **WM:** z-order, fokus, przeciąganie, min/max, dock. Proste, ale działa.
- **Userland i ABI** (`include/gemos/*`, `userland/common/*`, `uterm2`, `about`, `textedit`): najbardziej spójny i najlepiej napisany kod w repo; dobry kontrakt, wokół którego można przebudować jądro.

## 8. Rekomendacja: **remont, nie rewrite** — ale z przepisaniem 4 modułów

### 8.1 Uzasadnienie

1. **Skala jest mała.** Po usunięciu martwych plików żywy kod jądra to około 11 tys. linii, userland około 2,3 tys. Na tej skali refaktor jest tańszy niż rewrite, a jednocześnie da się go zrobić dokładnie, plik po pliku.
2. **Najtrudniejsza praca integracyjna jest zrobiona i działa w runtime:** tryb chroniony, IDT, TSS, paging per proces, Ring 3, syscalle z walidacją, reaping, TTF, WM. Rewrite od zera przeszedłby dokładnie te same etapy i te same pułapki debugowania, żeby dojść do punktu, w którym projekt jest dziś.
3. **Problemy są w większości lokalne,** zamknięte w pojedynczych modułach: boot, sterta, ATA+GemFS, FPU. Jedyny problem przekrojowy to model współbieżności (nr 1). Da się go jednak wprowadzić ewolucyjnie jedną regułą architektoniczną, bez przepisywania całości (etap 3).
4. **Userland i ABI to najlepsza część kodu.** Są naturalnym „kontraktem”, wokół którego można przebudowywać jądro bez psucia aplikacji.
5. **Rewrite od zera miałby sens** tylko przy zmianie fundamentalnych decyzji: higher-half kernel, 64-bit, SMP, UEFI/Multiboot, GUI w userlandzie od pierwszego dnia. README wprost wyklucza te kierunki na teraz, a ryzyko „drugiego systemu” jest realne.

**Szczerze:** to nie jest kosmetyka. Około 1/4 kodu jądra trzeba napisać od nowa (boot chain ~680 l., sterta ~100 l., ATA+GemFS ~410 l., model syscalli i blokowania), około 17% usunąć, a resztę gruntownie wyczyścić. Jeśli autor nie chce trzymać się decyzji architektonicznych z README (GUI w jądrze, 32-bit, własny loader), wtedy rewrite staje się rozsądną alternatywą.

### 8.2 Kolejność remontu

**Etap 0 — siatka bezpieczeństwa (najpierw, zanim cokolwiek się ruszy)**
- CI: `make all` (ścieżka `gcc -m32`) plus automatyczny smoke-test w QEMU, taki jak w tym audycie: boot, asercje na logu szeregowym (`Window Manager Active`, brak `PANIC`), screendump, uruchomienie UTERM/ABOUT/UTEXTEDIT przez HMP i sprawdzenie `Spawned`/`Reaped`.
- Makefile: `-MMD`, odtwarzanie `gemos.img` przy każdym buildzie, twarda kontrola `kernel.bin ≤ limit loadera`, katalogi obiektów zgodne ze strukturą źródeł, `-fno-asynchronous-unwind-tables`.
- `LICENSE` (MIT) i `OFL.txt` dla Inter.

**Etap 1 — odchudzenie (niskie ryzyko, szybki zysk)**
- Usunąć pliki z §5 (poza kernelowym TextEdit, który zostaje do etapu 5), martwe funkcje, testy z jądra, komentarze z rozmów AI.
- Jeden `string.h`, jeden zestaw kodów klawiszy, ikony w jednym `.c`.
- `AGENTS.md` napisać od nowa na podstawie kodu albo usunąć i zostawić README jako jedyne źródło.

**Etap 2 — fundament: boot i pamięć**
- `entry.S`: zerowanie BSS i przekazanie struktury boot-info (E820, VBE, numer napędu) do `kernel_main`.
- PMM oparty o E820. Sterta i pula ramek wyliczane z rzeczywistej pamięci, jawny błąd przy zbyt małej ilości RAM.
- Nowy loader: LBA (INT 13h ext) i start z HDD, rozmiar jądra z nagłówka zamiast stałej, lista preferowanych trybów VBE z fallbackiem, detekcja BGA z fallbackiem na `memcpy`.
- ATA od nowa: IDENTIFY, timeouty, bit ERR, brak dysku to działający system bez FS zamiast zawieszenia.

**Etap 3 — współbieżność i izolacja (najważniejszy technicznie)**
- Jedna reguła: **syscalle nie modyfikują stanu GUI/FS bezpośrednio.** Wrzucają żądanie do kolejki obsługiwanej przez task 0 (lub dedykowany wątek jądra) i blokują proces do odpowiedzi. Tam, gdzie to niepraktyczne, krótkie sekcje krytyczne (`cli`/`sti` z zapamiętaniem stanu) w stercie, klogu i rejestrze okien.
- Idle task plus `TASK_BLOCKED` z wybudzaniem (blokujący `poll_event`), bezczynny task 0 przestaje zjadać kwanty.
- Stan FPU: `fxsave`/`fxrstor` albo leniwie przez `CR0.TS`. Skala UI całkowita (brak `float` w IRQ).
- Każdy wyjątek z CPL3 kończy proces, nie system. Pełny zrzut rejestrów przy panice jądra.
- Walidacja ELF odporna na przepełnienia. `CR0.WP=1`, oddzielne segmenty RX/RW dla userlandu, strony ochronne dla stosów jądra.
- Nowy alokator sterty: scalanie w obie strony, magic/canary w nagłówkach, osobny pool dla drobnych alokacji fontów.

**Etap 4 — storage**
- GemFS v3: superblok z magic i wersją; montowanie tylko przy poprawnej sygnaturze; formatowanie tylko świadomie (np. osobny obraz `data.img` tworzony przez narzędzie hosta); bitmapa alokacji; pliki większe niż 8 KB; spójne API katalogów.
- Seeding ELF-ów tylko gdy ich brak lub zmieniła się wersja. Ładowanie ELF bez stałego bufora 8 KB.
- Uprawnienia minimum: pliki systemowe tylko do odczytu dla procesów.

**Etap 5 — GUI i aplikacje**
- Clipping tekstu do `clip_rect`, ograniczanie okien do ekranu, kaskadowe rozmieszczanie, monospace (albo pozycjonowanie per komórka) w konsoli hostowanej, tytuły menu, ikony, działające „Shutdown” lub usunięcie tej pozycji.
- UTEXTEDIT: open/save przez istniejące `SYS_file_read/write` (logikę można przenieść ze starego `apps/textedit`). **Dopiero potem** usunąć kernelowy TextEdit.
- Explorer: uruchamianie `.ELF`, poprawne asocjacje, docelowo przeniesienie do userlandu.
- Wydajność: dirty rectangles zamiast pełnego repaintu 1080p w każdej klatce.

**Czego nie robić teraz:** nie przenosić całego GUI do userlandu, nie dodawać sieci, USB ani SMP i nie dokładać nowych funkcji, dopóki etap 3 nie jest skończony. Każda nowa funkcja na obecnym modelu współbieżności zwiększa liczbę miejsc, które trzeba będzie potem przepisać.

## 9. Jak odtworzyć wyniki

```bash
# toolchain (Ubuntu): nasm + qemu; cross-kompilator opcjonalny
sudo apt-get install nasm qemu-system-x86
make clean && make all                        # ścieżka awaryjna gcc -m32

# start headless z monitorem
dd if=/dev/zero of=/tmp/data.img bs=1M count=10
qemu-system-i386 -drive file=build/gemos.img,if=floppy,format=raw \
  -drive file=/tmp/data.img,if=ide,format=raw -m 128M -display none \
  -serial file:serial.log -monitor unix:mon.sock,server,nowait
# w monitorze: screendump desktop.ppm / mouse_move dx dy / mouse_button 1 / sendkey ret
# uwaga: QEMU kolejkuje maks. ~5 pakietów PS/2 na zdarzenie, więc ruszaj myszą krokami ≤ 60

# bez dysku (jak make debug): zawieszenie w ata_read_sector
qemu-system-i386 -drive file=build/gemos.img,if=floppy,format=raw -m 128M -display none -serial stdio

# mało RAM: start pada po włączeniu pagingu
qemu-system-i386 ... -m 20M ...

# martwy kod: na kopii repo
make all CFLAGS="<flagi z Makefile> -ffunction-sections -fdata-sections" \
         LDFLAGS="-m elf_i386 -T linker.ld -nostdlib --gc-sections --print-gc-sections"
```

Zrzuty ekranu z QEMU (pulpit, UTERM, ABOUT, UTEXTEDIT, Explorer) przekazałem w sesji. Nie dodawałem ich do repo, żeby jedyną zmianą w drzewie był ten plik.
